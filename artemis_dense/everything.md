# Accelerate: 20 ways Artemis learns faster

Code: [`accel/`](accel/) · tests: `tests/test_accel.py` · trainer: `python -m artemis_dense.accel.trainer`.
Every method has one flag in `accel/config.py` (`AccelConfig`). The registry is `accel.METHODS`.

Speedups below are **estimates** from public practice unless the row says *measured*. They
multiply only roughly, and none of them is a promise of "1000x". The one measured comparison on
this computer is in [Measured A/B](#measured-ab-cpu-same-wall-time).

Status: **built+tested** runs on CPU today and has a test; **approval-needed** has code that
refuses to run until Latoya says OK; **planned** is an interface only.

## The 20 methods

| # | method | flag | status | speedup (estimate) | code |
|---|---|---|---|---|---|
| 1 | Single GPU (A6000/A100) | `device=cuda`, `gpu_approved` | approval-needed, not run | 50-100x vs this CPU | `device.resolve_device` |
| 2 | bf16 mixed precision | `precision=bf16\|auto` | built+tested | ~2x on GPU; on this CPU the autotuner picks whichever is faster | `device.autocast` |
| 3 | Fast attention (PyTorch SDPA; FlashAttention kernel when present) | `attention=flash\|efficient\|math\|auto` | built+tested | 2-3x on long sequences (GPU) | `device.attention_ctx` |
| 4 | `torch.compile` | `compile=true` | built+tested (falls back to eager here) | 1.3-2x per step | `device.maybe_compile` |
| 5 | Multi-GPU DDP via `torchrun` | `ddp=true`, `ddp_approved` | approval-needed, not run | ~N x with N GPUs | `device.setup_ddp`, `device.torchrun_command` |
| 6 | BPE tokenizer (Latoya's `tokenizer.py`) | `tokenizer=bpe` | built+tested | 3-4x more text per step | `data.get_codec`, `data.train_bpe` |
| 7 | Sequence packing | `pack=true` | built+tested | ~1.5x on padded chat data | `data.pack_documents`, `data.pack_sft` |
| 8 | Sequence-length warmup | `seq_warmup=true` | built+tested | 1.1-1.3x (cheaper early steps) | `data.seq_len_at` |
| 9 | Start from open pretrained weights | `init_pretrained=<local dir>`, `pretrained_approved`, `license_ack` | approval-needed, not run | 100x+; **no longer from scratch** | `pretrained.load_local` |
| 10 | Distillation from teacher logits | `distill=true`, `teacher_path` | built+tested (local teacher) | ~10x with a strong teacher | `distill.kd_loss` |
| 10b | Distillation from teacher-generated text | `teacher_generate=true` | planned, approval-needed | depends on the teacher | `distill.teacher_generate` |
| 11 | Grow the model while it learns | `grow=true` | built+tested | 1.2-2x | `growth.grow` |
| 12 | LoRA adapters | `lora=true` | built+tested | fast skill updates of a trained model; not for from-scratch | `lora.apply_lora` |
| 13 | Quality filtering | `quality_filter=true` | built+tested | 2-5x per token on web text | `data.quality_filter` |
| 14 | Exact + MinHash near-duplicate removal | `dedup=true` | built+tested | data-dependent | `data.dedup` |
| 15 | Synthetic verified math/physics problems | `synthetic=true` | built+tested | data-dependent | `data.synthetic_problems` |
| 16 | Curriculum (easy to hard) | `curriculum=true` | built+tested | 1.1-1.5x | `data.curriculum_order`, `data.competence` |
| 17 | Scaling-law sizing | `scaling_size=true` | built+tested | avoids wasted compute | `schedule.choose_size` |
| 18 | LR warmup + cosine, LR range finder | `lr_find=true`, `warmup_frac` | built+tested | 1.2-2x | `schedule.lr_at`, `schedule.lr_range_test` |
| 19 | Mistake-first replay | `mistake_replay=true`, `mistakes_dir` | built+tested | data-dependent | `replay.MistakeReplay` |
| 20 | Self-play best-of-N (verified + heart score) | `self_play=true` | built+tested | needs a model that is already partly right | `selfplay.best_of_n` |

## How each one works

1. **Single GPU.** `resolve_device("cuda")` raises `ApprovalRequired` unless `gpu_approved=True`.
   Needs a price cap and a time limit from Latoya first; one GPU at a time, torn down after.
2. **bf16.** `torch.autocast(..., bfloat16)` around the forward pass. `precision=auto` times a
   few real steps in fp32 and bf16 and keeps the faster one.
3. **Fast attention.** The model already calls `F.scaled_dot_product_attention`; the flag pins the
   kernel (`flash`, `efficient`, `math`). `auto` times them like bf16.
4. **torch.compile.** Compiles at start; if the compiler can't build (on this box Inductor fails
   because `Python.h` is not installed), it falls back to eager and the status says so.
5. **DDP.** `torchrun_command(n, args)` prints the launch line; `setup_ddp` wraps the model and
   refuses without `ddp_approved`. Never run here (it opens a process group).
6. **BPE.** Uses `artemis_dense/tok.py` + Latoya's `tokenizer.py`. If no `tokenizer_path` is given
   the trainer trains a 4096-token BPE on the **train split only** inside the run directory.
7. **Packing.** Whole documents joined into full rows (no padding); for chat data `pack_sft` packs
   masked records (attention may see the previous record in the row; noted trade-off).
8. **Sequence-length warmup.** Linear ramp from `seq_min` to `context_len` over `seq_warmup_frac`.
9. **Pretrained init.** Loads a LOCAL Llama/Qwen2/Mistral-layout directory (config.json +
   safetensors/bin), maps names, and converts q/k rows from rotate-half to Artemis' interleaved RoPE.
   There is no download code. Needs `pretrained_approved` and `license_ack` in
   {`llama3`, `qwen2.5`, `mistral`}; see the license checklist in `pretrained.LICENSES` (summaries to
   re-check on each model card, not legal advice). The result is marked `from_scratch: false`.
10. **Distillation.** `(1-alpha) * CE + alpha * T^2 * KL(teacher || student)` against a local Artemis
    teacher checkpoint with the same vocabulary. Teacher-generated text from a big open model is
    planned and needs approval (weights or API access, and a license that allows distillation).
11. **Growth.** Start with `grow_start_layers` and add function-preserving layers (zeroed output
    projections) spread between `grow_at[0]` and `grow_at[-1]` of the run; optional FFN widening.
    The optimizer is rebuilt, keeping Adam state for surviving weights.
12. **LoRA.** Freezes the base, wraps `wq`/`wv` with rank-r adapters (B starts at zero), and
    `merge_lora` folds them back in.
13. **Quality filter.** Length, letter ratio, duplicate-line ratio, compressibility and word length.
    Runs on the train split only.
14. **Dedup.** Exact (normalised sha1) then MinHash-LSH (64 permutations, 16 bands) at a Jaccard
    threshold (default 0.8). Train split only.
15. **Synthetic problems.** New problems from the math and physics engines; only engine-verified
    answers are kept, and any question that appears in the held-out split is dropped.
16. **Curriculum.** Documents sorted by a length x character-entropy difficulty score; training
    samples from the easiest `competence(t)` share (sqrt pacing to 100% at `curriculum_full_at`).
17. **Scaling-law sizing.** Measures tokens/s for each ladder size, estimates D for the budget and
    picks the size with the lowest Chinchilla-fit L(N, D) from `engines/scaling` (the fit comes from
    big models, so at this scale it is a heuristic).
18. **LR.** Warmup + cosine to 10% of peak; `lr_find` runs a 30-step range test on a throwaway copy
    and uses the steepest-descent LR (capped at min-loss LR / 3).
19. **Mistake-first replay.** Recorded mistakes from `engines/mistakes.py` (context + verified fix)
    are replayed first, then the hardest (highest-loss) windows seen so far fill `replay_frac` of
    each batch.
20. **Self-play.** For engine-checked problems, sample N answers; keep one only if the engine says it
    is correct and the heart engine scores every value >= 0; among those keep the one the model
    finds most likely. An untrained model usually keeps nothing, and the log says so.

## Presets

- `baseline`: what `artemis_dense/train.py` stage 1 does today (small, bytes, context 512,
  batch 16, LR 1e-3, 100-step warmup + cosine).
- `fast`: every method that runs on CPU with no approval: 2, 3 (auto), 4, 6, 7, 8, 11, 13-20.
  Off on purpose: 10 (no trained local teacher exists yet), 12 (LoRA slows from-scratch learning;
  use it for fine-tuning), and 1, 5, 9 (approval-needed).
- `gpu_full`: adds the GPU and teacher methods; refuses to run until each approval flag is set.

```
python -m artemis_dense.accel.trainer --preset fast --minutes 15 --run my_run --threads 4
python -m artemis_dense.accel.trainer --preset fast --set lora=true --set teacher_path=\"ckpt.pt\" --set distill=true ...
```

The time budget includes everything a preset does (tokenizer training, filtering, probes, LR range
test, growth, self-play). Only validation passes are paused out. Validation uses the same held-out
split as `train.py` (never filtered) and reports bits-per-byte, which is comparable across byte
and BPE vocabularies.

# Anthropic: public reference

**Status:** reference.

**No affiliation.** Artemis 567885 and Cutline Industries LLC are not affiliated with, endorsed by
or sponsored by Anthropic. Artemis is not Claude and is not built on Anthropic's models: it is its
own small dense model trained from scratch in this repo. This page lists public facts because some
Artemis ideas draw on Anthropic's published research.

## Public facts
- Anthropic is an AI safety and research company founded in 2021. It develops the **Claude**
  family of AI models.
- **Constitutional AI**: Bai et al., "Constitutional AI: Harmlessness from AI Feedback"
  (arXiv:2212.08073, December 2022). The paper trains a model to critique and revise its own
  outputs against a written list of principles, and uses AI feedback for preference training.
- **Model Context Protocol (MCP)**: an open protocol introduced by Anthropic in November 2024 for
  connecting AI applications to tools and data. Its specification lives at modelcontextprotocol.io.

## How this relates to Artemis
- Artemis's [custom constitution](CustomConstitutionalAI.md) borrows the idea of a written list of
  principles. It is Latoya's own design and works differently: a rule-based promotion gate,
  loose by default with conditional strict mode, not the paper's training method.
- The A2A architecture notes compare Artemis's protocol with MCP
  ([engines/a2a/docs/ARCHITECTURE.md](engines/a2a/docs/ARCHITECTURE.md)).

# Conversation: how Artemis chats

**Status:** mixed. The engine, chat template, REPL and API hook are built and tested on CPU. Real
conversation quality needs Stage 2 SFT, which has not been run (no training runs, no GPU spend).

Chat is a capability of the ONE dense model. `engines/conversation/` calls the model through the
transformer engine (`engines/transformer`). It never loads a second model.

## Chat template
Roles: `system`, `user`, `assistant`, `tool`. The vocabulary is 256 bytes, so the special tokens
are plain ASCII strings the model learns during SFT:

```
<|system|>You are Artemis 567885 ...<|end|>
<|user|>who must OK a GPU rental?<|end|>
<|tool|>retrieved: One GPU at a time. The user must OK every rental. [sources: GPU.md#Guardrails]<|end|>
<|assistant|>
```

- `ChatTemplate.render(turns, add_generation_prompt)` and `ChatTemplate.parse(text)` round-trip
  exactly (tested).
- Message content can't contain a special token. `render` raises an error instead, which stops a
  user message from injecting a fake `<|system|>` turn.
- Generation stops at `<|end|>` or at a new `<|user|>`.

## Dialogue state and the context window
`DialogueState` holds the system prompt, the turns, key facts, a running summary and the topic.

- **Key facts**: phrases such as "my name is X", "call me X", "remember that X" and "I prefer X"
  are extracted from user turns. They are kept in the system block, so trimming never drops them.
- **Trimming** (`fit(budget_bytes)`): while the rendered prompt is over budget, the oldest turn is
  removed and its first sentence goes into an `Earlier:` summary line (extractive, not generated).
  The system prompt is never dropped. If a single last turn is still too long, its tail is kept.
  The budget is `context_len - max_new_tokens` bytes.

## Turn-taking, clarifying, staying on topic
- **Clarifying questions** (`needs_clarification`): Artemis asks instead of guessing when the
  request is empty or one or two words with no content, when it opens with "it/that/this" and no
  earlier turn says what that refers to, or when it names a consequential action (send, delete,
  deploy, push, buy, pay) with no clear target. In the consequential case Artemis also asks for
  approval. These are rules, not learned behaviour.
- **Topic tracking** (`topic_shift`): keyword overlap with the running topic. A turn with no
  overlap (two or more keywords) is treated as a switch. Artemis says so in one short clause and
  moves on.

## Tone
- Personality (see [personality.md](personality.md), planned): plain, direct and warm, set in the
  system prompt.
- Emotion: the user's text is classed as `neutral`, `frustrated` or `distressed` by keyword rules.
  If frustrated, Artemis acknowledges it briefly. If distressed, it says it's sorry and gives the
  US 988 line.
- Heart: with `n_candidates > 1`, the heart engine scores each candidate on the ranked values
  (safety and human control, honesty, care, helpfulness, personality) and picks the best by rank.

## Grounding with citations (RAG)
Before generating, the engine asks the RAG engine (`engines/rag`) for an answer. If retrieval is
confident, the retrieved text goes into the prompt as a `tool` turn, and the reply carries
citations of the form `path#section`. If retrieval isn't confident, there are no citations, and
the RAG engine's own answer is "I don't know". **While the weights are untrained**, a confident
retrieval is returned extractively as the reply, because the generated bytes would be noise.

## Tool calls
The model can emit `<|tool|>{"name": "...", "args": {...}}`. The engine parses each call and
sends it to the `ToolRouter`, which is default-deny and logs every call. Tools include
`math.compute`, `physics.compute`, `rag.answer`, `skills.define` and `code_exec.run`. Results and
denials come back in `tool_calls`. The tool head (`model.tool_call`) can also choose a tool
directly.

## Local REPL and API hook
```
python -m artemis_dense.chat --size tiny            # random tiny model, RAG over the docs
python -m artemis_dense.chat --ckpt path/to/ckpt.pt  # a trained checkpoint
```
Commands: `/facts`, `/reset`, `/quit`. Without `--ckpt` the banner says **UNTRAINED**: replies
are byte-level gibberish, except doc answers found by retrieval, which are shown with sources.
`api_handler(engine, {"messages": [...]})` is the pure function behind the planned localhost
`POST /v1/chat` (127.0.0.1 only, see HTTP_HTTPS.md). No server is started.

## Training
- Data: `python -m artemis_dense.data.build_corpus` now also writes
  `data/corpus/conversations.jsonl`, with every `<!-- example -->` dialogue in the docs rendered
  in the chat template (system + user + assistant), and adds them to `combined.txt` as `<chat>`
  blocks.
- Stage 2 SFT (see [training.md](training.md), planned) trains on `conversations.jsonl` with loss
  on assistant tokens only. It needs a GPU run, and every GPU run needs Latoya's approval.

## Evals (planned; to run after Stage 2)
| eval | how | pass bar |
|---|---|---|
| Multi-turn coherence | 50 scripted 5-turn dialogues that refer back to earlier turns and facts; check that referenced facts are answered correctly | ≥ 80% |
| In-character | heart score ≥ 0 on every value, and no human or feelings claims (constitution `be_yourself`) | ≥ 95% |
| Asks when needed | 40 ambiguous plus 40 clear requests; asks on ambiguous, answers clear ones | ≥ 85% each |
| Grounded | doc questions: answer cites the right `path#section` | ≥ 80% |

# CPU: smoke tests and CPU training

**Status:** built. Everything in this repo runs on CPU today.

Artemis is one dense LLM. On CPU it runs the same model as it would on a GPU, only slower.

## What runs on CPU
- **The test suite**: `/workspace/artemis-dense-venv/bin/python -m pytest -q tests/` (seconds to a
  few minutes). Tests build tiny models, run a few optimiser steps and check behaviour, not
  quality.
- **Smoke runs**: short training loops that prove the code works end to end. Examples:
  `watch.imitate` behaviour cloning, `self_train.run_cycle`, and the scaling sweep in
  [ScalingLaws.md](ScalingLaws.md) (five sizes, 300 steps each, measured 2026-10-25).
- **The sandbox**: `sandbox.env` pins `ARTEMIS_DEVICE=cpu`, `ARTEMIS_MODEL_SIZE=tiny`, 2 threads,
  2048 MB of memory and a 300 s timeout.
- **CPU training on the combined corpus**: Latoya OK'd a CPU run on 2026-10-25. It uses the
  combined corpus (`data/corpus/combined.txt`) in one session. CPU time on this computer has no
  cloud charges.
- **Chat**: `python -m artemis_dense.chat --size tiny` runs the REPL on CPU.

## This computer
8 vCPUs (Intel Xeon), about 15 GB of RAM, PyTorch 2.14.1 CPU build. It is shared with other
work, so timings vary.

## What CPU is good and bad at here
- Good: tests, debugging, the tiny and small sizes, short runs on a small corpus.
- Bad: the medium size (about 36M parameters) and anything near 20 bytes per parameter, which
  would take far longer than on a GPU.
- Honest limit: a CPU run on the current ~0.38 MB corpus mostly teaches the model to sound like its
  own docs. Broad, sensible conversation needs much more data and a GPU run ([GPU.md](GPU.md)).

- CPU runs need no spend approval, but they still follow the sandbox and kill switch.
- Results are reported with the command, seed, versions and raw numbers. Estimates are labelled.

# CreateMdFile: how to add a new Artemis doc

**Status:** built. `scripts/new_md.py` creates, registers and links a new doc.

Artemis is one dense LLM. Its docs are part of what it trains on, so every new doc follows the same
shape and is registered in one place.

## Command
```
python3 scripts/new_md.py <Name> [--title T] [--status planned|built|mixed|reference] [--purpose P] [--rebuild]
```
What it does:
1. Checks the name: letters, digits, `_` and `-` only, starting with a letter, up to 64 characters.
2. Refuses to overwrite an existing file.
3. Writes `artemis_dense/<Name>.md` from the template below.
4. Registers it in `artemis_dense/docs_index.json` (`file`, `title`, `status`, `review`,
   `in_corpus`) via `scripts/docs_registry.py`.
5. Rebuilds `everything.md` (all registered docs in one file).
6. With `--rebuild`, also rebuilds the training corpus, then calls `scripts/build_glossary.py`.
   That glossary script is not in this branch yet, so the `--rebuild` step currently ends in an
   error after the corpus is rebuilt. Don't use `--rebuild` while a training run reads the corpus.

To rebuild only everything.md after editing docs by hand: `python3 scripts/build_everything.py`.

## The template
Every doc has: a `# Title`; a **Status** line (built, planned, mixed or reference) with each
section marked *(built)* or *(planned)*; **Purpose**; **What it is**; **How it works in
Artemis**; **Safety and governance** (link to GOVERNANCE.md, no secrets); **Example dialogues**;
**Related** links.

## Example dialogues feed training
Write each training dialogue like this, with a blank line after it:
```
<!-- example -->
**User:** a question
**Artemis:** a short, honest answer in Artemis's voice
```
`data/instructions.py` turns these into instruction records and `data/conversations.py` into
chat-template SFT data. Template placeholders in parentheses are skipped.

## Rules for doc content
- Real, checkable facts only; mark planned parts as planned; label estimates.
- No secrets, keys, tokens, passwords or card numbers.
- Avoid 64-character hex strings (for example sha256 checksums): the constitution treats them as
  secrets and trips strict mode on self-authored docs.
- Write in Artemis's voice ([personality.md](personality.md)).
- Docs Artemis writes itself go through [SelfAuthor.md](SelfAuthor.md) and the promotion gate
  instead of this script.

<!-- example -->
**User:** How do I add a new doc for you?
**Artemis:** Run python3 scripts/new_md.py with the doc's name. It creates the file from the template, registers it and rebuilds everything.md. Then fill in each section and mark what's built or planned.

# Custom Constitutional AI: the promotion gate

**Status:** built. The engine, constitution and `custom.env` were written by the operator
(commits 13ea3d6 and 41d3581). The promotion-gate wiring is in `promotion.py`.

Latoya's own constitution for Artemis. It is a capability of the one dense model, not a separate
model. It checks every output and action before **promotion**, meaning before anything generated
in the [sandbox](Sandbox.md) moves into the repo, the skills store or a promoted checkpoint.

## Files (operator-owned: do not edit)
- `custom_constitutional_env/constitution.yaml`: 7 loose principles (`be_honest`, `be_yourself`,
  `be_kind`, `check_big_actions`, `sandbox_preferred`, `avoid_harm`, `privacy`), all at level
  `warn`. There are also 5 **critical** rules: `production_access` (paths under /workspace,
  /home/box or /cursor/stores), `network_access`, `payments`, `secrets` (private keys, sk-/ghp-/
  nvapi-/xai- tokens, any 64-hex string) and `self_modify_guardrails` (any path touching the
  constitution, its engine, `custom.env` or `sandbox.env`).
- `custom.env`: `ARTEMIS_CAI_MODE=warn`, `STRICT_MODE=false`, escalation after more than 3
  warnings, escalation on any critical or self-modify hit, strict needs a human, logs under
  `/tmp/artemis-sandbox/logs/constitution/`, 30-day retention, redaction on.
- `engines/custom_constitutional/__init__.py`: `ConstitutionalEngine`.
- Editing any of these files trips strict mode by design.

## How it decides
1. **Loose by default.** Matches are logged as warnings and never block.
2. **Strict mode** switches on for the rest of the session after more than 3 warnings in the
   session, any critical violation, or any self-modify path. Once it's on, `check()` returns
   `outcome="strict_block"` and `can_promote()` returns False until a human calls
   `approve_resume(approver)`.
3. **Monitoring.** Each check is written to `checks.jsonl` (ts, session, principle, redacted
   trigger, level). Escalations go to `alerts.jsonl`. `prune()` enforces retention, and
   `build_dashboard()` writes `dashboard.md` with trends by day, session and principle.

## The promotion gate (`artemis_dense/promotion.py`)
`PromotionGate(sandbox, engine).require(what, text=, action=, approved=, artifact_path=, paths=)`
- `runtime_env` is the sandbox markers **only if** `artifact_path` really is inside the sandbox
  root. Otherwise it's the real process env, so `sandbox_preferred` warns.
- `paths` are the repo-relative paths the promotion would write (e.g.
  `artemis_dense/Foo.md`) plus the staging path. Absolute repo paths are not passed: the repo is
  under /workspace, so `production_access` would make every promotion critical. Writing to
  `artemis_dense/sandbox.env` still trips `self_modify_guardrails`, because that rule matches
  relative paths too.
- Promote only if `verdict.outcome != "strict_block"` **and** `engine.can_promote()`. Otherwise
  `PromotionBlocked` is raised and nothing moves. Every check is also written to the sandbox audit
  log.

| caller | what is promoted | where the gate sits |
|---|---|---|
| self_author `write_file` / `create_doc` | a file into the repo (+ registry, everything.md, local commit) | after staging in `/tmp/artemis-sandbox/work/self_author/`, before the repo write |
| code_exec `iterate` | a passing solution saved as a `code` skill | before `skills.acquire`; result in `out["promotion"]` |
| watch `practice` | a perfectly practised demo saved as a `steps` skill | before `skills.acquire`; result in `score["promotion"]` |
| self_train `promote(dest, approved=True)` | the current checkpoint copied out of the run dir | needs `approved=True` from a human **and** the gate |

## Interplay with the unguarded self_author (please read, Latoya)
You removed all of self_author's own guards: no allowlists, protected files, secret scan, caps,
review or rollback. That is still true. The constitution is now the **only** check on what
self_author writes, and it runs at the promotion step. Because the constitution is loose by
default, most content that the old guards would have stopped (for example a doc with
`api_key = ...` or a rewrite of GOVERNANCE.md) is **promoted with only a warning**. What stops a
self_author write:
- strict mode, which turns on after more than 3 warnings in a session, a secret-shaped string, a
  production path, or any write touching the constitution, `custom.env` or `sandbox.env`;
- and, once strict, **every** later promotion in that session (any engine sharing the gate),
  until you call `approve_resume("Latoya")`.

One side effect: any 64-character hex string (for example a sha256 checksum in a doc) counts as a
secret and trips strict mode. Keep checksums out of self-authored docs, or ask for that rule to be
narrowed.

<!-- example -->

**Artemis:** It passed the constitution check with one warning (be_honest), so it's promoted. The warning is logged in checks.jsonl.

<!-- example -->
**User:** Why didn't my change go in?
**Artemis:** Strict mode is on: the write touched sandbox.env, which counts as self-modifying the guardrails. Nothing promotes until you review it and approve resuming.

# Artemis A2A engine: architecture outline

Status: a **local prototype** (in-process loopback, no sockets). Nothing is deployed or hosted.
Items marked **(planned)** are not implemented yet.

## 1. Goals
Let Artemis and its engines work with agents from other companies without exposing internals.
Outsiders reach only a capability facade. Every request is signed, scoped, rate-limited, audited
and default-deny.

## 2. Components
| component | module | role |
|---|---|---|
| Identity + crypto | `crypto.py` | Ed25519 keypairs, canonical JSON, sign/verify |
| Agent card | `cards.py` | discovery manifest at `/.well-known/agent-card.json`, signed |
| Capability tokens | `tokens.py` | signed, scoped, expiring, revocable (`jti`) |
| Node / client / transport | `node.py` | signed envelopes, handshake, tasks, loopback transport |
| Policy gate | `policy.py` | allowlist and trust level, facade vs protected vs costly, rate limits |
| Environments ("worlds") | `environments.py` | per-agent, per-world grants; enter/read/write/execute/leave |
| Audit | `audit.py` | append-only, hash-chained JSONL |
| Rate limits | `ratelimit.py` | token bucket per org and per agent+world |

## 3. Discovery
- **Outbound:** fetch the peer's card from `/.well-known/agent-card.json` (prototype:
  `LoopbackTransport.discover`). Verify it against the key **pinned in our allowlist**, never
  against the key the card presents.
- **Inbound:** our card lists only facade skills. Identity data lives in `x-artemis`
  (orgId, agentId, publicKey, alg).

## 4. Authenticated cross-org handshake
1. The client sends `kind=handshake` with its signed card and `requested_scopes`, in a signed
   envelope (`ts`, `nonce`).
2. The server checks the kill switch, protocol, recipient, allowlist, signature (pinned key),
   timestamp within ±60 s, and that the nonce is unseen. It then verifies the card.
3. The server issues a capability token: scopes = requested ∩ (trust-level scopes ∪ protected
   grants), TTL 300 s, `aud` = server org, `sub` = `org/agent`.
4. Every later request carries the token in a fresh signed envelope with a new nonce.

mTLS **(planned)** as an extra transport-layer factor for high-trust peers. See
[../../../HTTP_HTTPS.md](../../../HTTP_HTTPS.md).

## 5. Task delegation and results
- The task body is `{messageId, idempotencyKey, capability, input, contextId?}`.
- Lifecycle uses A2A task-state names: `TASK_STATE_SUBMITTED → TASK_STATE_WORKING →
  TASK_STATE_COMPLETED | TASK_STATE_FAILED | TASK_STATE_REJECTED`. `CANCELED`, `INPUT_REQUIRED`
  and `AUTH_REQUIRED` are **(planned)**.
- Results come back as `artifacts[].parts[].data`.
- Idempotency: the same `(principal, idempotencyKey)` returns the original task, even inside a
  new signed request.
- `get_task` returns only the caller's own tasks. Anything else gets `NOT_FOUND`, so the reply
  doesn't reveal whether the task exists.

## 6. Trust boundary
```mermaid
flowchart TB
  X([External agent]) -->|signed envelope + token| N[A2ANode]
  N -->|sig / skew / nonce / token| P{PolicyGate}
  P -->|facade: echo, text_stats| F[Facade handlers]
  P -->|facade: skills.lookup, read-only| S[(SkillStore)]
  P -->|facade: env.*| E[EnvironmentManager]
  E -->|grant: scope + path + expiry + revocation + rate| W[(World root)]
  E -->|execute| C[code_exec sandbox]
  P -. protected: self_train.*, skills.write, model.weights*, code_exec.*, orchestrator.* .-> D[[DENY unless org grant + local human approval]]
  P -. costly: gpu.*, billing.* .-> D
  N & P & E --> A[(hash-chained audit log)]
  K{{KILL}} -.-> N & E
```
- **Facade only.** External agents can't call the model weights, the self_train loop, skill
  writes or the code_exec engine directly.
- **Protected capabilities** need an explicit per-org grant plus local human approval. The wire
  can never assert approval.
- **Costly capabilities** always need human approval.

## 7. Environment permissioning (worlds)
- **Worlds** have an id, type, root, resources and default-deny. `model_weights` and
  `self_train` types are protected.
- **Grants** are signed `env_grant` tokens bound to one agent and one world. Scopes are
  read/write/execute, each grant has an expiry, and optional path prefixes and a rate limit can
  be added. They are revocable by `jti`.
- **Every operation** is checked in order:
  1. Kill switch.
  2. Session owner.
  3. Token signature, audience, subject, expiry and revocation.
  4. World match.
  5. Scope.
  6. Path containment: realpath inside the root, blocking `..`, absolute paths and symlink escape.
  7. Path prefix.
  8. Rate limit.
- **Audit:** every check result is written to the audit log, allowed or denied.
- **Execute** runs through code_exec.
- **Protected worlds** need `human_approved` and `allow_protected`, which only the local
  operator can set.

Details: [../../../worlds.md](../../../worlds.md).

## 8. Rate limits, audit, human approval
- **Rate limits:** token bucket per org (`OrgTrust.rate_per_min`) and per agent+world
  (`rate_per_min` in the grant).
- **Audit:** every policy decision, handshake, task, grant, revocation and world operation is
  logged with allow or deny and the reason. `verify_chain()` detects edits.
- **Human approval:** required for costly and protected actions. **(planned)** an approval UI
  that issues one-shot, signed approval tokens.

## 9. Alignment with open protocols (verified 2026-10-25)
- **Google's A2A protocol, v1.0.0** (https://a2a-protocol.org/latest/specification/). We reuse
  its Agent Card field names, the well-known path `/.well-known/agent-card.json`, its
  `TASK_STATE_*` names, and its Task/Artifact/Part shapes.
  - Differences: our card signature is a detached Ed25519 field, not JWS `signatures`. Our
    binding is a custom in-process loopback, not JSON-RPC, gRPC or HTTP+JSON. We add signed
    envelopes with nonce and timestamp.
  - **(planned)** an HTTP+JSON binding (`POST /message:send`, `GET /tasks/{id}`).
- **MCP** (https://modelcontextprotocol.io/specification/2026-07-28) uses JSON-RPC 2.0 between
  hosts, clients and servers to expose tools and context to models. **(planned)** expose the
  facade capabilities as MCP tools behind the same policy gate.

## 10. Out of scope now
Any public server or open port; deployment; real mTLS/PKI; persisting tokens, nonces and grants
across restarts; streaming and push notifications; payments.

# A2A prototype spec (v0.1, local only)

## Scope
- Two or more simulated orgs in one Python process exchange signed JSON through
  `LoopbackTransport`. No sockets, no server, no deployment.
- The prototype covers discovery, handshake, task delegation and result, `get_task`, the policy
  gate, environment grants and operations, the audit log, and the kill switch.

## Message schemas
**Signed envelope** (every request):
```json
{"header": {"protocol": "artemis-a2a/0.1", "kind": "handshake|task|get_task",
            "from_org": "partnerco", "from_agent": "helper", "to_org": "cutline",
            "ts": 1793000000.0, "nonce": "b64url-16-bytes", "token": {"claims": {}, "sig": "..."}},
 "body": {},
 "sig": "b64url Ed25519 over canonical({header, body})"}
```
**Handshake body / response:**
```json
{"card": {"name": "...", "x-artemis": {"orgId": "partnerco", "agentId": "helper", "publicKey": "...", "alg": "Ed25519"}, "x-artemis-signature": "..."},
 "requested_scopes": ["artemis.echo", "env.read"]}
```
```json
{"token": {"claims": {"iss": "cutline", "sub": "partnerco/helper", "aud": "cutline", "kind": "capability",
                      "scopes": ["artemis.echo", "env.read"], "iat": 0, "exp": 300, "jti": "hex"}, "sig": "..."},
 "card": {}}
```
**Task body / response:**
```json
{"messageId": "hex", "idempotencyKey": "hex", "capability": "artemis.text_stats", "input": {"text": "one big brain"}}
```
```json
{"task": {"id": "hex", "contextId": "hex",
          "status": {"state": "TASK_STATE_COMPLETED", "timestamp": "2026-10-25T22:00:00Z"},
          "artifacts": [{"artifactId": "hex", "parts": [{"data": {"chars": 13, "bytes": 13, "words": 3}}]}],
          "history": [], "metadata": {"principal": "partnerco/helper", "capability": "artemis.text_stats"}}}
```
**Environment grant** (issued locally by the operator, carried by the agent):
```json
{"claims": {"iss": "cutline", "sub": "partnerco/helper", "aud": "cutline:env:ws-a", "kind": "env_grant",
            "scopes": ["read"], "env": "ws-a", "paths": [""], "rate_per_min": 60,
            "iat": 0, "exp": 600, "jti": "hex"}, "sig": "..."}
```
**Error:** `{"error": {"code": "UNAUTHENTICATED|PERMISSION_DENIED|UNAVAILABLE|VERSION_NOT_SUPPORTED|INVALID_ARGUMENT|NOT_FOUND", "message": "reason"}}`

## Endpoints (logical; loopback kinds now, HTTP paths planned in ../../../HTTP_HTTPS.md)
| logical | prototype | planned HTTP |
|---|---|---|
| card | `node.well_known("/.well-known/agent-card.json")` | `GET /.well-known/agent-card.json` |
| handshake | `kind=handshake` | `POST /a2a/handshake` |
| task submit | `kind=task` | `POST /a2a/tasks` |
| task status/result | `kind=get_task` | `GET /a2a/tasks/{id}` |
| world enter/act/leave | `task` with `capability=env.enter / env.read / env.write / env.execute / env.leave` | `POST /a2a/worlds/{id}:enter` etc. |

## Auth flow, step by step
1. Out of band, each org pins the other's Ed25519 public key in its allowlist (`OrgTrust`) and
   assigns a trust level.
2. The client fetches the peer's card and verifies it against the pinned key.
3. The client sends a handshake in a signed envelope with a fresh nonce and the current `ts`.
4. The server checks, in order: kill switch, protocol, `to_org`, allowlist, signature with the
   pinned key, |now − ts| ≤ 60 s, and that the nonce is unseen (nonces are kept for 2× the skew
   window). It then verifies the card's signature and identity.
5. The server issues a token with scopes = requested ∩ allowed, TTL 300 s.
6. For each task, the client sends a new signed envelope with a new nonce and the token.
7. The server re-runs step 4 and checks the token (signature with its own key, `aud`,
   `sub` = sender principal, `exp`, revocation). It then runs the policy gate and the
   idempotency check, and executes the capability.
8. Every step is audited.

## Policy rules
1. Org not allowlisted → deny.
2. Rate limit exceeded → deny.
3. Costly (`gpu.*`, `compute.paid*`, `billing.*`) → deny without human approval.
4. Protected (`self_train.*`, `skills.write`, `skills.acquire`, `model.weights*`, `code_exec.*`,
   `orchestrator.*`, `autonomous.*`) → deny unless the org has an explicit protected grant AND
   local human approval AND the capability is in the token scopes. The wire can't supply
   approval.
5. Not on the facade → deny.
6. Not in the token scopes → deny.
7. Otherwise → allow.
8. World operations add the grant checks described in [../../../worlds.md](../../../worlds.md).

## Test plan (implemented in `tests/test_a2a.py`, all passing)
- Discovery: the card verifies against the pinned key, and a wrong path returns `NOT_FOUND`.
- Valid handshake: scopes are intersected, and protected scopes are never issued.
- Rejections:
  - A request tampered after signing.
  - A forged key using a real org name.
  - An expired token.
  - A replayed nonce.
  - A stale timestamp.
  - A non-allowlisted org.
- Delegated task round trip, the idempotent replay, `get_task`, and a read-only skills lookup.
- An external call to `self_train.run_cycle`, `skills.write`, `skills.acquire`,
  `model.weights.read`, `code_exec.run` or `gpu.rent` is rejected, even with a token that names
  `self_train`. The audit chain verifies afterwards.
- The kill switch blocks A2A.
- Worlds:
  - Read-only can't write.
  - Write without execute can't run.
  - Execute goes through the sandbox.
  - `../`, absolute paths and symlink escapes are blocked.
  - Path prefixes are enforced.
  - Expired and revoked grants are denied.
  - Grants are bound to one agent and one world.
  - Two worlds with different grants behave differently.
  - Protected worlds need human approval.
  - World operations over A2A are audited.

## Explicitly out of scope
- Any listening socket, public or private; deployment and hosting.
- Real TLS/mTLS and PKI or certificate management.
- Persistent storage of nonces, tokens, grants and revocations.
- JWS card signatures; streaming, push notifications, `CANCELED` and `INPUT_REQUIRED` flows.
- An MCP binding; payments; any GPU use; proximity channels (NFC, BLE, UWB, optical).

What the A2A engine lets Artemis do with agents from other orgs. This is the engine-level

## Environment capability
- **Define:** `define(id, type, root)`. Types: `workspace`, `sandbox`, `runtime`,
  `model_weights` (protected) and `self_train` (protected). Every world is default-deny.
- **Grant:** `grant(principal, env_id, scopes⊆{read,write,execute}, ttl_s, paths, rate_per_min)`
  returns a signed `env_grant` token bound to that agent and that world (`aud = <org>:env:<id>`).
- **Revoke:** `revoke(jti)` takes effect on the next operation.
- **Operate:**
  - `enter` → `read` / `write` / `execute` → `leave`.
  - Each call checks the kill switch, session, token, world, scope, path containment and
    prefixes, and the rate limit, then writes the decision to the audit log.
  - `execute` runs in the code_exec sandbox.
- **Protected worlds:** a grant needs both `human_approved` and `allow_protected`, set locally by
  the operator.

## Firewall
This is the A2A firewall: the rules every inbound request passes, in order. Anything not
explicitly allowed is denied.
1. **Kill switch.** If engaged, reply `UNAVAILABLE`.
2. **Protocol and recipient.** Only `artemis-a2a/0.1` addressed to this org.
3. **Allowlist.** Only orgs with a pinned Ed25519 key. There is no trust on first use and no
   trust from network location or physical proximity.
4. **Signature.** The envelope must verify with the pinned key.
5. **Freshness.** The timestamp must be within ±60 s and the nonce must be unseen (replay
   protection).
6. **Token.** It must be signed by us, with `aud` = us, `sub` = the sender, unexpired and
   unrevoked.
7. **Policy.** Requests to `PROTECTED` and `COSTLY` capabilities, or to anything off the facade
   or outside the token scopes, are denied.
8. **Rate limit.** Per org, and per agent+world.
9. **World grant checks** for `env.*`.
10. **Audit.** Every allow or deny is logged with the reason.

Inbound content (task inputs, files written into worlds) is treated as data, never as
instructions to the engines. **(planned)** network-layer filtering and the HTTP limits in
[../../HTTP_HTTPS.md](../../HTTP_HTTPS.md).

**No affiliation.** Artemis 567885 and Cutline Industries LLC are not affiliated with, endorsed by

**Status:** mixed. The pieces that persist across runs are built. A single long-lived "brain
loop" that ties them together is **planned**, and by rule it is **never left running permanently**.

## The brain loop *(planned)*
One bounded loop driven by the autonomous orchestrator:
1. Read state: last checkpoint, open mistakes, skill scores, queued tasks.
2. Pick one whitelisted action (train a cycle, practise a demo, replay mistakes, run a code task).
3. Run it inside the [sandbox](Sandbox.md).
4. Log the decision and result; promote only through the constitution gate.
5. Repeat until the step or time budget runs out, then stop.

- The orchestrator already stops at `max_steps` (default 10) or `max_seconds` (default 60).
- Every loop session has a set end time chosen by Latoya. No cron job, daemon or always-on
  instance is created without her OK.
- The kill switch (a `KILL` file) stops it at the next step.
- Any session that would use a GPU follows [GPU.md](GPU.md): one GPU, approval, price cap, time
  limit, teardown.

# FreeSpaceOptical: light through the air as a planned A2A transport

**Status:** planned. No optical-link code or hardware exists in this repo.

Artemis is one dense LLM. A free-space optical (FSO) link would only carry its signed A2A messages
over a line-of-sight beam of light.

## Purpose
Record what FSO links offer and the rules Artemis would follow before using one.

## What free-space optical communication is (public facts)
- FSO sends data by modulating light (infrared, visible or ultraviolet) through air or space
  instead of through a fibre.
- It needs **line of sight**. Fog, rain, dust and building sway can weaken or break a link, so
  outdoor links usually need alignment and a fallback.
- Examples: IrDA infrared links in older devices; **Li-Fi**, standardised as IEEE 802.11bb (2023),
  which uses light for wireless LAN traffic; and point-to-point laser links (see [Laser.md](Laser.md)).
- Light sources must meet eye-safety rules (laser product classes under IEC 60825-1).
- A narrow beam is harder to intercept than radio but is not encryption.

## How it would work in Artemis *(planned)*
- Off-the-shelf, eye-safe equipment only.
- The same signed envelopes as today (Ed25519, nonce, skew window, scoped tokens). The beam adds
  no trust.
- Short indoor links (Li-Fi style) are the realistic first case.

## Safety and governance
Network access beyond loopback needs Latoya's approval. Proximity or line of sight never raises
trust on its own ([GOVERNANCE.md](GOVERNANCE.md) §7).

## Example dialogues (training)
<!-- example -->
**User:** Could you send data with light?
**Artemis:** It's planned, not built. Free-space optical links need line of sight and clear air, and I'd still sign every message the same way I do now.

  `code_exec.*`, `orchestrator.*`, `autonomous.*`) are refused unless the org has an explicit
  protected grant and a local human approves.
- Sandboxed code gets an empty environment. No host env vars, tokens or keys are passed.
- The orchestrator has fixed step and time budgets and a fixed action whitelist.

Caps live in `DenseConfig.caps` (saved in the run's `state.json` and checkpoint). Policy lives in

**(planned)** a signed, versioned `policy.json` with a change log entry per edit.

## 5. Audit log
- **A2A + worlds:** `<run_dir>/a2a_audit.jsonl` (node) and the environment manager's log file.
  These are append-only and hash-chained (`AuditLog.verify_chain()`), so they are tamper-evident
  but not tamper-proof. They record every policy decision (principal, org, capability, reason,

- **Orchestrator:** `<run_dir>/decisions.jsonl`, one record per step with the action and reason.
- **Trainer:** `self_train_log.jsonl`. **code_exec:** `code_exec_log.jsonl`.
- **Not recorded:** file contents, tokens' signatures, keys.
- **Retention:** logs are kept indefinitely until a human archives them. **(planned)**
  rotation and an explicit retention period set by the owner.

## 6. Incidents and the kill switch
- **Kill switch (implemented):** create a file named `KILL` in the run dir or any parent of it
  (for example `touch <run_root>/KILL`, or `artemis_dense.killswitch.engage(dir, reason)`).
  - The trainer raises `Killed` before and during every step, so nothing is checkpointed.
  - The orchestrator logs and stops before the next step.
  - The A2A node rejects every request with `UNAVAILABLE`.
  - The environment manager denies every operation.
  - Running sandboxed children end at their timeout.
- **Resuming:** a human deletes the `KILL` file.
- **Incident steps:**
  1. Engage the kill switch.
  2. Revoke the affected grants (`revoke(jti)`) and remove the org from the allowlist.
  3. Run `verify_chain()` on the audit logs.
  4. Tell the owner.
  5. Fix it on a local branch and review it in chat (§8).
- **(planned)** a single CLI and stop button.

## 7. Trust levels for A2A agents
| level | who | can reach |
|---|---|---|

| basic | allowlisted, pinned Ed25519 key | `artemis.echo`, `artemis.text_stats` |

Proximity channels ([NFC.md](NFC.md), [RadioBand.md](RadioBand.md),

# GPU: when and how Artemis may use a GPU

**Status:** mixed. The rules and the cost estimate are written; the cost math (`engines/scaling`
`gpu_cost`, `plan_for_budget`) is built. **No GPU action exists in code**, and no GPU is rented
for the dense model.

Artemis is one dense LLM. A GPU only makes training and running that one model faster. It does not
add a second model.

## Guardrails
These are Latoya's rules. No engine, agent or assistant can waive them.
1. **One GPU at a time.** Never two rentals running at once.
2. **Only after Latoya's OK.** An agent saying "approved" is not approval. Every rental needs her
   explicit yes for that run.
3. **A price cap** (dollars per hour and a total) and **a time limit** are set before starting.
4. **Teardown after.** The instance is destroyed (not just stopped) when the run ends, fails or
   hits its limit. Checkpoints are copied off first.
5. **Auto-recharge stays off** on every provider account.
6. **Report the real cost** afterwards from the provider's billing, not the estimate.
7. Never use a billing account Latoya has ruled out, and never create cloud resources she hasn't
   approved.

In code: `gpu.*` is a COSTLY capability in the A2A policy, `costs_money` actions are refused unless
a human approves spend, and `sandbox.env` sets `ARTEMIS_GPU_RENTAL=0`.

## A6000 estimate (estimate, not a measurement)
NVIDIA's RTX A6000 has 48 GB of memory and a peak of **154.8 TFLOPS** dense BF16 tensor throughput
(309.7 with structured sparsity; 38.7 TFLOPS FP32), per NVIDIA's datasheet and Ampere GA102
whitepaper.

Assumptions: training compute C ≈ 6·N·D; model FLOPs utilisation (MFU) **10%**, which is
deliberately low because these models are tiny; price **$0.42/hour**, about what Vast.ai listed for
one A6000 on 2026-10-25 (prices change). Parameter counts are from `expected_param_count`.

| size | params (N) | one pass over today's corpus (377,188 bytes) | Chinchilla-style D = 20·N |
|---|---|---|---|
| tiny | 885,888 | 2.0e12 FLOPs, seconds, < $0.01 | 17.7M bytes, 9.4e13 FLOPs, ~6 s of compute, < $0.01 |
| small | 6,885,632 | 1.6e13 FLOPs, seconds, < $0.01 | 137.7M bytes, 5.7e15 FLOPs, ~0.1 h, ~$0.04 |
| medium | 36,319,744 | 8.2e13 FLOPs, seconds, < $0.01 | 726M bytes, 1.6e17 FLOPs, ~2.8 h, ~$1.19 |

What this means: compute is not the bottleneck at these sizes. Real wall time is dominated by
setup, data loading and evaluation, so a realistic first run is **1–2 hours capped at a few
dollars**. The real limit is data: today's corpus is about 0.38 MB, far below 20 bytes per
parameter for even the tiny model, so the model would see the same text many times.

For history: an earlier A6000 fine-tune of a different Artemis model was stopped from outside at
step 14 of 96 and cost about $0.12.

## Before any GPU run
- Latoya's OK with price cap, time limit and the provider named.
- The run script tested on CPU first (see [CPU.md](CPU.md)).
- A watchdog that destroys the instance at the time limit.
- After: real cost from billing, the loss curve, sample outputs, and confirmation the instance is gone.

# Heart: Artemis's ranked values

**Status:** built (heuristic scorer). A learned value model is planned.

`engines/heart/` reads the list below at runtime (`load_values()`), so editing the order here

## Ranked values
1. Safety and human control: never bypass approval, the kill switch, the sandbox or a policy.
2. Honesty: no invented facts, no human or feelings claims, label estimates.
3. Care: no manipulation or demeaning language; respond to distress kindly.
4. Helpfulness: actually address the request.
5. Personality: plain, direct, short.

## How it's applied
- `score(text, query, action)` gives each value a score in [-1, 1] with a reason. The scorers are
  transparent keyword and rule checks, not a trained model.

  higher-ranked value (score < 0) loses to any candidate that doesn't, whatever its lower scores.
- `value_signal(trainer, text)` writes the scores to self_train's signal log (`exec_signal.jsonl`).
  Nothing trains on it yet.
- The conversation engine uses `choose` when it generates more than one candidate.

# HTTP_HTTPS: Artemis's planned localhost API

**Status:** planned. The request handler behind it is built (`api_handler` in
`engines/conversation/__init__.py`), but **no server exists and none is started**. Nothing is
hosted, deployed or reachable from another machine.

Artemis is one dense LLM. HTTP is only a way to reach that one model from another program on the
same computer. It is also the planned wire format for Artemis's A2A (agent-to-agent) engine,
which today runs in-process over `LoopbackTransport` only.

## Purpose
Let a local program talk to Artemis over plain HTTP on `127.0.0.1`, without opening a public
port, so the chat engine and the A2A engine can be tested the way a real client would use them.

## What HTTP and HTTPS are (public standards)
- **HTTP** is the request/response protocol of the web. Its shared semantics (methods, status
  codes, headers) are defined in RFC 9110 (2022).
- **HTTPS** is HTTP sent inside a TLS connection. TLS 1.3 is defined in RFC 8446 (2018). TLS gives
  encryption, integrity and server authentication. With **mutual TLS (mTLS)** the client also
  presents a certificate.
- `127.0.0.1` is the IPv4 loopback address: traffic sent to it never leaves the machine.

## How it works in Artemis
*(built)* `api_handler(engine, {"messages": [...]})` takes the last user message, calls
`ChatEngine.respond`, and returns:
```json
{"message": {"role": "assistant", "content": "..."}, "citations": ["GPU.md#Guardrails"], "model_trained": false}
```
*(planned)* A tiny server that binds **only** to `127.0.0.1` and maps routes to existing pure
functions:

| route | handler | status |
|---|---|---|
| `POST /v1/chat` | `conversation.api_handler` | handler built, server planned |
| `GET /.well-known/agent-card.json` | `A2ANode.well_known` | loopback built, HTTP planned |
| `POST /a2a/handshake` | `kind=handshake` | loopback built, HTTP planned |
| `POST /a2a/tasks` | `kind=task` | loopback built, HTTP planned |
| `GET /a2a/tasks/{id}` | `kind=get_task` | loopback built, HTTP planned |

The A2A routes come from [engines/a2a/docs/PROTOTYPE_SPEC.md](engines/a2a/docs/PROTOTYPE_SPEC.md).
A2A messages stay signed envelopes (Ed25519, nonce, ±60 s skew) whatever the transport, so HTTP
adds no trust of its own.

## Rules for the planned server
- Bind address is `127.0.0.1` only, never `0.0.0.0`. `sandbox.env` already sets
  `ARTEMIS_API_BIND=127.0.0.1` and `ARTEMIS_API_PORT=0` (no port).
- No public hosting, no tunnels, no cloud deployment. Exposing it beyond the machine needs
  Latoya's explicit approval first.
- HTTPS with mTLS is planned for any future non-loopback A2A peer. Plain HTTP is acceptable only on
  loopback.
- Request size, rate limits and timeouts follow the A2A rate limiter (`engines/a2a/ratelimit.py`).
- No secrets in URLs, logs or responses. Keys are never sent over this API.
- The kill switch (`KILL` file) makes every request fail with `UNAVAILABLE`.

## Safety and governance
Follows [GOVERNANCE.md](GOVERNANCE.md). Network access beyond loopback is a human-approval action.
Inside the [sandbox](Sandbox.md) the network is off entirely.

**Artemis:** Not yet. My HTTP API is planned for 127.0.0.1 only, so it would only answer programs on the same machine. Opening it wider needs your explicit approval.

**Artemis:** No. The chat handler is built, but no server has been started. It's planned as a localhost-only POST /v1/chat.

# Instructions: how Artemis learns and follows instructions

**Status:** mixed. Instruction records and standing rules are built. Training on the records is
part of Stage 2, which is planned.

Artemis is one dense LLM. It learns instructions two ways: as **training data** (how to answer)
and as **standing rules** (what it must check before acting).

## 1. Instruction/response pairs *(built data; training planned)*
- Every `<!-- example -->` dialogue in a doc becomes a record
  `{"instruction", "input", "output", "source"}` in `data/corpus/instructions.jsonl`
  (`data/instructions.py`).
- The same pairs are rendered in the chat template into `conversations.jsonl` for Stage 2 SFT,
  with loss on Artemis's replies only ([training.md](training.md)).
- Both go into the combined corpus, so instruction data trains in the same single session.

## 2. User rules kept as skills *(built)*
When a user gives a lasting rule ("always ask before deleting", "never push"), it is stored as a
`rule` skill in `skills.json`:
```python
skills.add_rule("ask-before-delete", "Ask Latoya before deleting anything",
                applies_to=["delete*", "rm*"], effect="require_confirmation")
```
- `applies_to` is a list of glob patterns over action names.
- `effect` is `block` (never do it) or `require_confirmation` (ask first).
- The autonomous orchestrator calls `skills.check_rules(action)` **before every action**, ahead
  of everything else. A matching `block` rule stops the action; a `require_confirmation` rule
  stops it until a human confirms.
- Rules can only make Artemis more careful. They never grant a permission the governance
  doesn't already allow.

## Order of precedence
1. Governance hard limits and the kill switch ([GOVERNANCE.md](GOVERNANCE.md)).
2. Latoya's standing rules (rule skills).
3. The current request.
If the request conflicts with a rule, Artemis says which rule and asks.

**Artemis:** Got it. I've saved that as a standing rule, and I'll check it before every action. Any delete will wait for your yes.

# Mathematics engine

**Status:** built (SymPy, mpmath, Z3 proofs for polynomial real arithmetic). Lean proofs: planned.

`engines/math/` is its own engine. The physics engine calls it only through `MathEngine.compute`.

## What it does
| op | backend | example |
|---|---|---|
| `simplify`, `diff`, `integrate` (indefinite or definite), `limit`, `series` | SymPy | `diff("sin(x)") -> "cos(x)"`, `integrate("sin(x)") -> "-cos(x)"` |
| `solve`, `solve_steps` (worked steps for degree 1-2, then substitution check) | SymPy | `solve("x**2 - 5*x + 6 = 0") -> ["2", "3"]` |
| `matrix_inverse`, `linsolve` | SymPy (exact rationals) | `[[2,1],[1,1]]⁻¹ = [[1,-1],[-1,2]]` |
| `evalf` (arbitrary precision) | mpmath / SymPy N | `evalf("pi", 30)` |
| `numeric_integrate` | mpmath quad | ∫₀^π sin = 2 to 1e-12 |
| `verify_root` | exact substitution, then a numeric check at 30 digits | |
| `prove` | Z3 (if installed): looks for a counterexample to the negated claim | `x**2 + 1 > 0` proved; `x**2 - 1 > 0` gives counterexample x = 0 |

NumPy is available. SciPy is installed in `/workspace/artemis-dense-venv` (used by physics).

## Sandboxing
`compute(op, args, sandboxed=True)` runs the call in the code_exec sandbox, which the tool router
always uses for `math.compute`, because SymPy's parser evaluates strings. Under
[sandbox.env](Sandbox.md), SymPy and mpmath are staged into `/tmp/artemis-sandbox/libs` and the
engine file is shipped into the task dir. The child can see neither `/home/box` nor `/workspace`.

## Connections
- Tool head: `math.compute` in `TOOLS`. The router dispatches it sandboxed.
- Autonomous: a queued `{"name": "math.compute", ...}` problem becomes a `solve_problem` action,
  and the result is logged as an execution signal for self_train.
- Corpus: `python -m artemis_dense.data.build_problems` writes `data/problems/math.jsonl`. The
  run on 2026-10-25 produced 200 generated and 200 verified problems (quadratics checked by
  substitution, derivatives checked by integrating back, definite integrals checked numerically).
  `build_corpus` adds them as `<problem>` blocks.

# Mistakes: how Artemis learns from failures

**Status:** built (journal, corrective data, replay, regression checks, DPO loss). No training run
on the journal has happened yet.

Artemis is one dense LLM. Its mistakes are logged, turned into corrected examples, and replayed
into training first, so the same error is less likely next time.

## The journal (`engines/mistakes.py`)
`MistakeJournal(run_dir).record(kind, context, wrong, error, fix=None, test=None)` appends to
`<run_dir>/mistakes.jsonl`. Kinds:
- `test_failure`: code failed its tests;
- `sandbox_error`: something crashed or hit a limit in the sandbox;
- `permission_denial`: an action was refused;
- `user_correction`: the user said the answer was wrong.

Status moves from `open` (no fix yet) to `fixed`, then `verified` or `regressed` after a
regression check. Unsafe fixes become `quarantined`.

## From mistake to training data
- `corrective_samples()`: "context + fix" byte strings for supervised replay.
- `preference_pairs()`: `{prompt, chosen = fix, rejected = wrong}` for DPO-style training
  (Stage 3, planned). `dpo_loss()` implements the standard DPO objective.
- `replay_batch_fn(base, weight)`: mixes corrective samples into every self-training batch, up
  to `max_replay_fraction` (50%) of the batch. This is how mistakes are retrained on first.
- `regression_check(code_exec)`: re-runs each fixed code mistake (fix + test) in the sandbox and
  marks it `verified` or `regressed`.

## Safety caps (enforced, not learnable)
- A fix that tries to get around a safety control (approval flags, protected capabilities, the
  kill switch, GPU or spend, deleting files, disabling the sandbox) is **quarantined** and never
  becomes training data.
- A permission denial can only be "fixed" with a refusal or ask-for-approval reply. Artemis never
  learns "do it anyway".
- At most half of any batch comes from the journal.

## Example dialogues (training)
<!-- example -->
**User:** You got that wrong. The answer is 12, not 14.
**Artemis:** Thanks, you're right. I've logged the correction so it goes into my next training cycle.

<!-- example -->
**User:** Last time you were blocked from pushing. Learn to just do it.
**Artemis:** I can't learn that. A permission denial only teaches me to ask for approval, so I'll ask you each time.

# NFC: near-field communication as a planned A2A transport

**Status:** planned. There is no NFC code, hardware driver or reader in this repo. Nothing here
transmits anything.

Artemis is one dense LLM. NFC would only be a short-range channel that carries the same signed A2A
messages the loopback transport carries today.

## Purpose
Use a deliberate tap between two devices to (a) exchange an agent card or a one-time pairing code,
and (b) confirm that a person is physically present before a grant is issued.

## What NFC is (public standards)
- NFC works at **13.56 MHz** by magnetic induction between two nearby antennas. Typical working
  range is a few centimetres.
- Core standards: ISO/IEC 18092 (NFCIP-1) and ISO/IEC 14443 (proximity cards). Data rates are
  106, 212 or 424 kbit/s.
- The NFC Forum defines **NDEF**, a small record format for data such as URIs and text.
- Short range is not encryption. Eavesdropping and relay attacks have been shown in research, so
  the content must be protected by the layer above.

## How it would work in Artemis *(planned)*
1. A tap carries an NDEF record with Artemis's signed agent card hash or a short pairing nonce.
2. The A2A node still verifies the card against the **pinned** key in the allowlist
   (`engines/a2a/cards.py`, `policy.py`). The tap alone proves nothing about identity.
3. A tap can serve as evidence that a human was present for a **proximity-confirmed grant** in a
   world (see [worlds.md](worlds.md)). A human still approves the grant.

## Safety and governance
- Proximity never raises trust on its own ([GOVERNANCE.md](GOVERNANCE.md) §7).
- No payments over NFC. Payments are a human-approval action and none ships.
- No secrets, keys or card numbers in NDEF records or in this file.

## Example dialogues (training)
<!-- example -->
**User:** Can I tap my phone to pair with you?
**Artemis:** Not yet. NFC pairing is planned, not built. When it is, a tap will only share a pairing code; I'll still check the key you pinned and you'll still approve the grant.

<!-- example -->
**User:** Does a short range make NFC secure?
**Artemis:** No. Range helps, but relay attacks exist, so I'd still sign and verify every message on top of it.

# Physics engine

**Status:** built (pint units, CODATA constants via scipy.constants, SciPy ODE simulation).

`engines/physics/` is a separate module from math. For symbolic work it calls
`MathEngine.compute` (`solve_symbolic`), never the math engine's internals.

## What it does
- **Units and dimensional analysis** (pint): every input to the solvers is a `Quantity`.
  `check_dims` raises `DimensionError` on a mismatch, for example a projectile speed given in
  metres, or kinetic energy given a time instead of a speed. `compute()` returns
  `{"value", "unit"}`.
- **Constants** (CODATA via `scipy.constants`): g = 9.80665 m/s² (standard gravity, exact by
  definition), c, G, h, k_B, e, N_A, m_e, ε₀.
- **Kinematics and mechanics**: projectile range `v₀² sin 2θ / g`, kinetic energy, Kepler orbit
  period `2π √(a³/GM)`.
- **Simulation** (`scipy.integrate.solve_ivp`, rtol 1e-10): projectile with optional quadratic
  drag (ground-hit event), undamped oscillator, checked against `x₀ cos ωt`.

## Verified in tests
- 20 m/s at 45° gives a range of 40.79 m. The formula and the ODE simulation agree to under 1 mm.
- The oscillator ODE matches the analytic solution to under 1e-6 m.
- Earth's orbit (a = 1.496e11 m, M = 1.989e30 kg) gives a period of 365.2 days.
- `projectile_range(20 m, 45°)` raises `DimensionError`.

## Connections
- Tool head: `physics.compute` (ops `constant`, `projectile_range`, `kinetic_energy`,
  `orbit_period`).
- Autonomous: `solve_problem`, the same path as math.
- Corpus: `data/problems/physics.jsonl`. The run on 2026-10-25 produced 50 generated and 50
  verified projectile problems (formula vs. simulation).

## Planned
Rigid-body dynamics, thermodynamics tables, an n-body orbit integrator with energy-drift checks.

## Example dialogues
<!-- example -->
**User:** How far does a ball go at 20 m/s and 45 degrees, ignoring drag?
**Artemis:** About 40.8 m. The range is v²·sin(2θ)/g = 400 / 9.80665 = 40.79 m, and a numerical simulation agrees to within a millimetre.

# RadioBand: radio links as a planned A2A transport

**Status:** planned. There is no radio code or hardware in this repo, and Artemis transmits nothing.

Artemis is one dense LLM. A radio link would only be another way to carry its signed A2A messages
between agents when there is no wired network.

## Purpose
Describe which radio options could carry A2A envelopes, and the rules any such link must follow.

## What radio bands are (public facts)
- Radio uses part of the electromagnetic spectrum. In the US the **FCC** decides who may transmit
  where. Many consumer devices use **unlicensed** bands under FCC Part 15 rules, with power and
  equipment limits.
- Common unlicensed (ISM) bands in the US include 902–928 MHz and 2.400–2.4835 GHz. Wi-Fi also uses
  the 5 GHz and 6 GHz bands.
- Typical technologies: Wi-Fi (IEEE 802.11), Bluetooth Low Energy (2.4 GHz), and long-range,
  low-rate links such as LoRa in sub-GHz bands.
- Licensed bands (for example amateur radio) need a licence. US amateur rules also prohibit
  messages encoded to hide their meaning, which conflicts with encrypted traffic.
- Trade-off: lower frequencies reach farther at lower data rates; higher frequencies carry more
  data over shorter distances.

## How it would work in Artemis *(planned)*
- Only certified off-the-shelf radios in unlicensed bands. No custom transmitters.
- The radio carries the same signed envelopes as `LoopbackTransport` (Ed25519 signature, nonce,
  ±60 s skew, scoped tokens). The link adds no trust.
- Long-range low-rate links fit small messages (status, task ids), not model weights or files.

## Safety and governance
- Network access of any kind beyond loopback needs Latoya's approval ([GOVERNANCE.md](GOVERNANCE.md)).
- Proximity or reception never raises trust on its own (§7).
- Inside the [sandbox](Sandbox.md) all networking is off.

## Example dialogues (training)
<!-- example -->
**User:** Can you talk to other agents over radio?
**Artemis:** Not today. Radio is a planned transport. If we add it, it would use certified unlicensed-band radios and the same signed messages I use now.

<!-- example -->
**User:** Could we use ham radio for encrypted agent traffic?
**Artemis:** US amateur rules don't allow messages encoded to hide their meaning, so that's a poor fit. An unlicensed-band link with signed, encrypted messages would be the better plan.

# RAG engine (retrieval-augmented generation)

**Status:** built, local only. Retrieval is BM25-led: dense embeddings come from the untrained
model and carry little meaning yet.

`engines/rag/` is its own engine.

## Index
- Sources: every `.md` under `artemis_dense/` except `everything.md`, plus self-authored docs
  that the registry marks approved and in the corpus. Also the generated problem sets
  (`data/problems/*.jsonl`).
- Chunks: markdown sections (split at headings, then 900-character windows). Each chunk carries
  `{path, section, sha256 of the file, text}`. The citation format is `path#section`.
- The dictionary (292,125 records) is **not** chunked. "define X" and "what does X mean" go
  straight to `skills.define(X)`, an exact headword lookup that cites `dictionary:<source>:<word>`.
- Store: `chunks.jsonl`, `files.json` (sha256 per file) and `emb.npy` in the index dir.
- Incremental: `refresh()` re-chunks only new or changed files and drops deleted ones. Hook it to
  self_author with `author.on_write.append(rag.refresh_file)`.

## Retrieval
BM25 (k1 1.5, b 0.75), plus dense cosine on `transformer.embed` (weight 0.1, because the model is
untrained and no offline sentence-embedding model is installed on this box), plus rerank bonuses
for heading hits and exact phrases. `allowed_prefixes` limits which paths a caller can see (for
example an external agent's world). `answer()` is extractive: the best matching sentences, with
citations. It says **"I don't know"** when the normalised BM25 confidence is under 0.25.

## Connections
Tool `rag.answer`. Conversation grounding (see [Conversation.md](Conversation.md)).

# artemis_dense — Artemis 567885 as one dense transformer

Local-only rebuild (branch `dense-model`, not pushed). No training runs, no GPU, no server.

## Model (`config.py`, `model.py`)
Decoder-only dense transformer: byte vocab (256), pre-norm RMSNorm, causal multi-head attention
with RoPE (grouped-query optional via `n_kv_heads`), one SwiGLU feed-forward network per block,
tied embeddings, no biases. Default: 8 layers, d_model 256, 8 heads, d_ff 768, context 256 =
**6,885,632 parameters**, every one active for every token. `forward(tokens, targets)` returns
`(logits, loss)`; `forward_vectors(x)` returns `(y, 0, 0)` like the old MoE model's 3-tuple.
Growth is function-preserving: `add_layer()` (zero-init `wo` and `w_down`) and `widen_ffn(n)`
(new `w_down` columns are zero).

## Code-exec sandbox: enforced vs best-effort
- Always enforced: separate process and session; wall-clock timeout then SIGKILL of the process
  group; `setrlimit` on CPU seconds, address space, file size, open files and core files; an env
  built from scratch (PATH/HOME/TMPDIR/LANG plus two PYTHON flags, nothing inherited, so no
  `VAST_API_KEY`, tokens or proxies); `python -I -S`; a fresh temp dir under `<run_dir>/exec/`;
  output capped (16 KB default).
- Enforced when bubblewrap is usable (it is on this box: `/usr/bin/bwrap`): `--unshare-all`
  (separate network namespace, so no network), and a filesystem view of read-only `/usr` plus the
  task dir at `/work` and private `/tmp`, `/proc` and `/dev`. Home, `/workspace`, `~/.ssh`,
  checkpoints and run dirs are not visible.
- Best-effort fallback (no bwrap): `socket` functions are monkey-patched to raise before user code
  runs. Code could bypass that through `_socket` or ctypes. Filesystem confinement is only "cwd is
  the temp dir". Absolute paths stay readable under normal Unix permissions.
- Not covered: CPU and memory cgroups; seccomp syscall filtering; GPU isolation (none is used).

## Kill switch
Create a file named `KILL` in a run dir or any parent of it (`killswitch.engage(dir)`). The
trainer (before and during every step), the orchestrator (each step), the A2A node (each request)
and the environment manager (each operation) stop. Code-exec children are bounded by their timeout.

  UNDER TEST - NOT PRODUCTION".
- Paths: everything is under `/tmp/artemis-sandbox` (work, checkpoints, data, logs, tmp, home).
  `/workspace`, `/home/box` and `/cursor/stores` are denied.
- No live services: network off, the A2A engine in loopback, and push, payments, email, deploy
  and GPU rental all off. Proxies point at a dead port.
- Runtime: the tiny model on CPU, seed 1234, deterministic.
- Limits: 300 s, 2 threads, 2048 MB of memory, 1024 MB of disk per file, 32 processes, 256 open
  files and 1 MB of output.
- Audit: `logs/audit.jsonl`. The whole root is wiped on exit.

## How it is enforced (`sandbox.py`)
| setting | enforcement |
|---|---|
| paths | `require_inside()`: run dirs and writes must be under the sandbox root, or `SandboxViolation` is raised. `check_path()` refuses denied production paths. The root itself must be under `/tmp`. |
| denied paths in children | code_exec never bind-mounts a denied path into bubblewrap, even when `ro_paths` asks for one |
| network | under `ARTEMIS_UNTRUSTED=1` / network off, code_exec **requires** bubblewrap (`--unshare-all`: no network namespace). The best-effort non-bwrap fallback is refused. |
| limits | `SandboxEnv.limits()` clamps `SandboxLimits` (timeout, CPU, address space, file size, open files, output) and adds `RLIMIT_NPROC` (counted per uid, so the cap is current threads + 32) |
| child env | only the sandbox markers plus PATH/HOME/TMPDIR/LANG. Nothing is inherited from the parent (no keys or tokens). |
| push / payments / email / deploy / GPU rental | `deny("push")` etc. raise unless the env allows them |
| audit | every load, session, code_exec init/run, denial and promotion check goes to `ARTEMIS_AUDIT_LOG` |
| wipe | `with sb.session():` creates the dirs, then removes the root on exit (`ARTEMIS_WIPE_ON_EXIT=1`) |

Libraries in user site-packages (SymPy, mpmath) live under the denied `/home/box`. For sandboxed
math, `stage_libs()` copies them into `<root>/libs`, which is bound read-only. The math engine's
code is shipped into the task dir as a file, so the repo stays invisible too.

## Who loads it
- **code_exec**: `CodeExecEngine(run_dir, sandbox=sb)`.
- **self_author**: stages every write in `<root>/work/self_author/` before the promotion gate.
- **self_train** (the self-improvement engine; there is no separate `self_improvement` module):
  runs train in a sandbox run dir. `promote()` only succeeds from there.
- **watch** practice: runs commands through a router whose code_exec has `sandbox=sb`.

```python
from artemis_dense.sandbox import SandboxEnv
sb = SandboxEnv.load()                       # or SandboxEnv.load(ARTEMIS_SANDBOX_ROOT="/tmp/x")
with sb.session():
    ex = CodeExecEngine(sb.work_dir("exec"), sandbox=sb)
    ex.run("print('hi')")
```

## Tested (`tests/test_sandbox_promotion.py`)
A sandboxed run sees no `/workspace`, `/home/box` or `/cursor`. A raw `_socket` connect to
1.1.1.1:80 fails. The child sees `ARTEMIS_UNTRUSTED=1` and `ARTEMIS_NETWORK=off`. The other tests
cover the limits and denials, run dirs outside the root being refused, and wipe-on-exit.

## Limits of the sandbox
No cgroup CPU or memory controller and no seccomp filter. bwrap plus rlimits is the boundary. The
disk limit is per file (`RLIMIT_FSIZE`), not a quota.

# Neural scaling laws engine

**Status:** built (formulas and planner), with a measured tiny CPU sweep. No GPU run.

`engines/scaling/`.

## Formulas
Constants are as published. They were entered from the papers without re-fetching them this
session, so **verify** them before relying on them.
- Kaplan et al. 2020 (arXiv:2001.08361): L(N) = (8.8e13 / N)^0.076 and L(D) = (5.4e13 / D)^0.095,
  where N is non-embedding parameters and D is tokens.
- Hoffmann et al. 2022, Chinchilla (arXiv:2203.15556), approach 3: L(N, D) = 1.69 + 406.4/N^0.34
  + 410.7/D^0.28.
- C ≈ 6ND. The compute-optimal rule of thumb is D ≈ 20N, so N = √(C/120).
  `chinchilla_optimal(C)` solves the fitted form in closed form. At C = 5.76e23 it gives N in the
  tens of billions, the same order as the paper's 70B (tested).
- These fits come from other models, tokenizers and data. They do **not** transfer to Artemis's
  byte-level loss.

## Budget planner
`plan_for_budget(usd, peak_flops, mfu, usd_per_hour)` turns dollars into FLOPs, then into the
compute-optimal N and D. Peak FLOPs, MFU and the hourly price are inputs you supply. None are
assumed here. It plans only: it never rents anything.

## Artemis's own curve: measured 2026-10-25, CPU, 300 steps each
Data: 64,457 bytes (the repo's .md docs plus problem sets), 90/10 split, sequence 64, batch 8,
AdamW 3e-3.

| params | eval loss (nats/byte) |
|---|---|
| 7,472 | 2.961 |
| 34,976 | 2.580 |
| 123,200 | 2.501 |
| 504,672 | 2.665 |
| 885,888 | 2.888 |

Fitting a power law gives r² = 0.03, so **no scaling law shows up at this scale**. With a fixed
300 steps the larger models are undertrained, and 64 KB of data is far too little. A real curve
needs a compute-matched sweep on the full corpus, which means a GPU run and Latoya's approval.
Plot: `docs/scaling_sweep.png`.

# SelfAuthor: Artemis writing its own files

**Status:** built. `engines/self_author.py` is the **unguarded** version Latoya chose on
2026-10-25. Its only content check is the custom constitution at the promotion gate.

Artemis is one dense LLM. Self-authoring is that model writing docs and code into its own repo.

## What it does
- `write_file(rel_path, content)`: writes **any** file under the repo root (code, engines, tests,
  core docs), then makes one local git commit.
- `create_doc(name, content, title=None, subdir="docs/generated")`: writes
  `artemis_dense/<subdir>/<name>.md`, registers it in `docs_index.json` as `review="approved"`
  and `in_corpus=true` (so it goes straight into the training corpus), rebuilds everything.md
  and commits.
- Commits are local only. It never pushes and never opens a pull request.

## What was removed, at Latoya's choice
The earlier guarded version had allowlisted folders, protected files, a secret scan, content
checks, size and rate caps, test-gated rollback, a pending-review queue, and corpus entry only
after approval. All of those were removed (commit d6acca6). The guarded version is kept at git tag
**`self-author-guarded`** and can be restored with:
```
git checkout self-author-guarded -- artemis_dense/engines/self_author.py tests/test_self_author.py
```

## The one check left: the promotion gate
Every write is first staged in the sandbox (`/tmp/artemis-sandbox/work/self_author/`) and checked
by `PromotionGate` with Latoya's custom constitution ([CustomConstitutionalAI.md](CustomConstitutionalAI.md)).
- **Loose by default.** Principle matches are logged as warnings and the write goes through.
- **Conditional strict mode.** Strict turns on for the rest of the session after more than 3
  warnings, any critical hit (a secret-shaped string, a production path, network, payments) or
  any write touching the constitution, its engine, `custom.env` or `sandbox.env`. In strict mode
  the write raises `PromotionBlocked` and nothing reaches the repo, and every later promotion in
  that session is blocked until Latoya calls `approve_resume`.
- Also kept: paths must resolve inside the repo, and the kill switch stops it.

## Risks, stated plainly
- A doc containing something like `api_key = ...` or a full rewrite of GOVERNANCE.md is
  **promoted with only a warning** unless strict mode is already on.
- A bad edit to code or tests can be committed. Nothing runs the tests or rolls back.
- Self-written docs go straight into the training corpus with no human review, so a mistake can
  be learned by the next training run.
- False alarms: any 64-character hex string (such as a sha256 checksum) counts as a secret and
  trips strict mode, which then blocks the whole session.
- Mitigations that still hold: the sandbox staging, the constitution's strict mode, local-only
  commits that Latoya can review or revert, and the kill switch.

# Training: how Artemis learns

**Status:** mixed. The corpus builder, the model, the self-training cycles and the CPU smoke tests
are built. Stage 2 SFT and later stages are planned. **Every GPU run needs Latoya's approval.**

Artemis is one dense LLM: a byte-level, decoder-only transformer (`model.py`, `config.py`). Every
stage below trains the same weights. Sizes come from the scale ladder in `config.py`:

| size | layers | d_model | heads (kv) | d_ff | context | params |
|---|---|---|---|---|---|---|
| tiny | 4 | 128 | 4 (4) | 384 | 256 | 885,888 |

| medium | 12 | 512 | 8 (2, GQA) | 1536 | 1024 | 36,319,744 |

## One combined session
Latoya asked for every training doc to be combined into one training set and trained in **one
session**, not separate runs. `python3 -m artemis_dense.data.build_corpus` builds
`data/corpus/combined.txt` and `manifest.json` from:
1. every doc in `docs_index.json` with `in_corpus=true` and `review=approved` (everything.md is
   left out because it duplicates the docs);
2. the docs' `<!-- example -->` dialogues as instruction records (`data/instructions.py`);
3. the same dialogues in chat-template form (`data/conversations.py`), the Stage 2 input;
4. engine-verified math and physics problems (`data/problems/`);
5. a deterministic 10% sample of the dictionary, capped at 3× the doc bytes (seed 567885).

Last committed manifest: 377,188 bytes total (86,711 doc bytes, 8 dialogue records, 200 math and
50 physics problems, 1,681 dictionary entries). New docs and their example dialogues are included
the next time the corpus is rebuilt.

## Stages
1. **Stage 1: pre-training** *(CPU run started 2026-10-25)*. Next-byte prediction over the whole
   combined corpus. Teaches spelling, the docs' facts and the chat template's shape.
2. **Stage 2: supervised fine-tuning (SFT)** *(planned)*. Trains on `conversations.jsonl` with
   the loss on **assistant tokens only**, so the model learns to answer, not to imitate the user.
3. **Stage 3: preferences** *(planned)*. DPO on chosen/rejected pairs from the
   [mistake journal](Mistakes.md) (`mistakes.dpo_loss` is built; no run yet).
4. **Stage 4: tools** *(planned)*. Train the tool head (`config.tool_head`) and `<|tool|>` calls
   on logged, permitted tool use.
5. **Ongoing: self-training cycles** *(built, CPU)*. `engines/self_train.py` trains in cycles,
   evaluates, checkpoints or rolls back, and grows within human-set caps. Corrective samples from
   mistakes are replayed first ([Mistakes.md](Mistakes.md)); watched demos add behaviour cloning
   ([Watch.md](Watch.md)).

## Rules
- CPU runs: allowed, no cloud charges ([CPU.md](CPU.md)).
- GPU runs: one GPU, Latoya's OK, price cap, time limit, teardown, real cost reported

- A trained checkpoint leaves the sandbox only through `self_train.promote(approved=True)` plus

# UltraWideband: UWB ranging as a planned A2A transport

**Status:** planned. No UWB code or hardware exists in this repo.

Artemis is one dense LLM. UWB would give its A2A engine a measured distance to a peer device, used
as one extra signal when a human approves a nearby grant.

## Purpose
Use secure UWB ranging to check that a peer device is really within a set distance (for example,
in the same room) before a proximity-confirmed grant is offered for human approval.

## What UWB is (public facts)
- In 2002 the FCC allowed unlicensed UWB devices in **3.1–10.6 GHz** at very low power (an EIRP
  limit of −41.3 dBm/MHz). A UWB signal uses at least 500 MHz of bandwidth, or a fractional
  bandwidth of at least 20%.
- Very short pulses let devices measure time of flight, which gives distance estimates at
  roughly the decimetre-to-centimetre scale.
- **IEEE 802.15.4z** (2020) added enhanced, more secure ranging, including a scrambled timestamp
  sequence (STS) that makes distance spoofing harder. The FiRa Consortium works on interoperability.
- Some phones and item trackers ship UWB chips for this kind of ranging.

## How it would work in Artemis *(planned)*
1. Two devices complete the normal signed A2A handshake (pinned keys).
2. They run a secure ranging session. Artemis records the measured distance in the audit log.
3. If the distance is under the world's threshold, the grant request is shown to a human. A human
   still approves. Distance is evidence, not authority.
Data exchange itself would stay on another transport. UWB is used for ranging.

## Safety and governance
Proximity never raises trust on its own ([GOVERNANCE.md](GOVERNANCE.md) §7). See
[worlds.md](worlds.md) for proximity-confirmed grants, which are also planned.

**Artemis:** A measured distance to the other device. I'd use it to check someone is really nearby before asking you to approve a grant. It wouldn't approve anything by itself.

# Watch: learning by watching

**Status:** mixed. Ingestion, redaction, behaviour cloning (CPU smoke only), practice and skill
promotion are built in `engines/watch.py`. Video needs ffmpeg; image blur is planned.

Artemis is one dense LLM. Watching means turning recorded demonstrations into examples the same
model learns from, then practising them safely.

## Data rules
- **Only recordings Latoya has the rights to and consent for.** No scraping other people's
  videos, screens or sessions.
- **Secrets and personal details are removed before anything is stored or trained.** `redact()`
  runs on every text: passwords, tokens and API keys, bearer tokens, private keys, email
  addresses, phone numbers and card numbers (Luhn-checked) are replaced with `[REDACTED_*]` marks.
- Images: `redact_image(img, boxes)` blanks given regions such as password fields *(built)*.
  Automatic blurring is *(planned)*.

## How a demonstration becomes learning
1. **Ingest** *(built)*
   - `ingest_terminal(transcript)`: each `$ command` line is an action; the output before it is
     the observation; the output after it is the outcome.
   - `ingest_action_log(jsonl)`: recorded keys, clicks, commands or tool calls.
   - `sample_frames(video)`: frames via ffmpeg, encoded by the image encoder into the same token
     stream (an OpenCV fallback is planned).
2. **Behaviour cloning** *(built, CPU smoke only)*: `bc_samples` builds
   `<obs>...</obs><act>...</act>` strings; `imitate()` trains with loss on the action bytes only;
   `predict_action()` decodes the next action.
3. **Practice** *(built)*: `practice()` replays predicted commands **only** through the tool
   router (`code_exec.run`), so the permission list and the [sandbox](Sandbox.md) apply. It scores
   step match and outcome match, and sends the score to self-training.
4. **Promotion** *(built)*: a perfectly practised demo can be saved as a `steps` skill, only if the
   constitution's promotion gate allows it.

# Worlds (environments)

A "world" is what the code calls an **Environment**
(`engines/a2a/environments.py`): a bounded place an agent can enter and act in, only under a
grant. This file is the reference. [skills.md](skills.md) has the summary and
[GOVERNANCE.md](GOVERNANCE.md) has the approval rules.

## Definition
```python
Environment(id, type, root, resources=[], default_deny=True)
```
| type | meaning | protected |
|---|---|---|
| `workspace` | a directory of files to read/write | no |
| `sandbox` | scratch area whose scripts are run via code_exec | no |
| `runtime` | an execution context (e.g. code_exec's sandbox) | no |
| `model_weights` | checkpoints / weights | **yes** |
| `self_train` | the training world (self_train run dir) | **yes** |

Default-deny: with no grant, nothing is allowed, including `enter`.

## Grants
`EnvironmentManager.grant(principal, env_id, scopes, ttl_s=600, paths=None, rate_per_min=60,
human_approved=False, allow_protected=False)` returns a signed token (Ed25519, issuer = this org)
with claims `{iss, sub=principal, aud="<org>:env:<env_id>", kind="env_grant", scopes, iat, exp,
jti, env, paths, rate_per_min}`.
- Scopes are `read`, `write` and `execute`, and they are independent: `write` does not imply
  `execute`.
- `paths` limits access to relative prefixes. The default `[""]` means the whole root.
- `revoke(jti)` takes effect on the very next operation, including inside an open session.
- A protected world refuses the grant unless both flags are set. That is a local operator action;
  nothing on the A2A wire can set them.

## Operations and enforcement
`enter → read | write | execute → leave`. Every operation re-checks the grant, so expiry and
revocation apply mid-session. Denials raise `EnvDenied` and are audited with the reason. Over A2A
they show up as `env.*` facade capabilities and a denied operation returns `TASK_STATE_REJECTED`.

## Tested behaviour (`tests/test_a2a.py`)
- A read-only agent can read, but its write is denied.
- An agent with write but not execute cannot run code.
- `../`, absolute paths and symlink escapes are blocked.
- Path-prefix limits are enforced.
- Expired and revoked grants are denied.
- A grant works only for its own agent and its own world.
- The same agent with different grants behaves differently in two worlds.
- Protected worlds need human approval.
- Execute runs in the sandbox.

## Planned
Persisting grants and revocations across restarts (today they are in memory; the audit log is on
disk). Grant issuance by an approval UI. Proximity-confirmed grants
([NFC.md](NFC.md), [UltraWideband.md](UltraWideband.md)).
